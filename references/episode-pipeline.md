# 单期制作流水线（强制顺序，2026-09-20 沉淀自 LOGIC-016/017 共 9 个修订版）

> 每一步都有"门"。门没过，不进下一步；尤其 **不生成语音、不生成图片、不渲染**。
> 门的产物写进私有进度库（evidence/…）与项目目录（script.json / storyboard.md / checks/），公开 Skill 只放规则。
> 用户明确说"先看文案""先看分镜"时，对应门必须由用户放行；用户没说，也要先自审过门再往下。

## 步骤 2：逻辑门（细则）

必须写一个小脚本（放 evidence/…/logic-checks.txt 或 script.json.logic_check），并满足：

1. **按文案原话建模**，不是按"我脑子里的题"建模。文案说"女友线 :00、妈线 :02"，脚本就用这两个数，算出"先来谁"的概率，与文案的结论比对。
2. **逐句举例**：对每个含具体数值/时刻/顺序的句子，至少举 1 个具体实例（到站 :01 → 先来谁；第 5 只摸到白 → 手里几只单），输出结果与文案该句逐字比对。写入 `logic_check.sentence_checks`。
3. **追问段同样模拟**（:05 → 50%；:08 → 翻转）。
4. **数字一致性**：文案里所有数字（30 天 = 24 + 6；三色各 10 = 30）互相加得上。
5. **前提合理**：情境里每个要求都有生活理由；不靠"加一个人物"来圆。
6. **一句话复述**：外行能一句话说出题目。
7. 渲染器常量命名带语义（`MOM_OFF / GF_OFF`），参数名与其真实控制的东西一致；改文案后 grep 所有 `t_of('…')` 锚点是否仍存在。
8. **叙事里的每个"改变物体状态"的动作都要进模型，不只建模题设规定的操作**（018 r1 事故：文案为了搞笑写"一口下去…辣的"，即从水杯喝了一口——水杯就不再是 100ml，"两杯都是一百毫升"为假，守恒等式被破坏；16 条检查全绿，因为脚本只建模了两次转移）。逻辑门脚本先列出文案中所有动词（舀/倒/喝/掉/吃/拿走），每个动词对应一次状态更新；梗也不能免检。
9. 文案初稿在写逻辑门前先过 `pipeline_check.py --stage 1`：它会量第二人称密度（≥12/千字）与首问估时（≤20s）。018 r1 曾写成"老爸/小王"第三人称、首问 28s，与已批准的 017 风格不一致，靠自审才发现。

## 步骤 3：文字分镜（细则）

模板：

```
| 段 | 时间 | 画面与动画 | 屏幕文字 |
```

必须满足：
- 首帧含题设道具；≤1s 一次画面事件；前 5s 台词含数字；无纯人物静帧；提问在 15–20s。
- 每段 ≥1 个独立动画事件；全片 ≥10 个（列出来数）。
- 屏幕文字只黑 + 单一强调色；字幕样式沿用锁定版。
- 素材清单：生成 = 物件数（不是状态数）；数量/计数/几何一律程序绘制。
- 构图：人物与标题分左右车道；数据图（时间轴/钟面）说明文字放图侧上方，不放图标运动路径下方。
- 幽默约4个/分钟（100秒约7处），每段至多一处，结论句与证明句不放梗。

## 步骤 7–8：自审（细则）

- `--preview` 的 collisions 只检测包围盒，**对人物 PNG 无效**；关键帧必须看图。
- 重新对齐音频后先 `rm -rf checks/ev-*` 再预览，避免看旧帧。
- 成片再抽一次帧（fps=1/6 tile）与前 6 秒（fps=2），因为渲染与预览路径可能不同。
- 自审表（问题 / 量测值 / 根因 / 处置）存进度库；没有表就没有自审。

## 步骤 0 / 10：占号与检查点必须同轮落地（2026-09-20，018 交接断链）

- **占号提交必须与检查点在同一轮完成**：018 曾出现 episodes.json 已写 `reserved_script_draft`、评审文件已推送，但 HEAD 仍停在上一个检查点、也没有 ask_user 记录的情况。下一模型只能看到"占了号"却无法证明"用户选过"。
- 占号条目最少包含：`selected_by_user: true`、`registered_at`、`proposal`（候选文件）、`juming`、`principle`；缺 `selected_by_user` 的占号视为未确认，接手者先向用户复核，不直接开做。
- 顺序：用户选择 → 写 episodes.json + 制作清单 → **写检查点（含选择来源）** → 一次提交推送 → 再开始文案。有文案/分镜提交也同样先追加检查点再结束回合。

## 步骤 5–9 工程坑（2026-09-20，018 沉淀）

- **环境**：沙箱快照会丢每个克隆的 `.git/config`（remote + user.name/email）——开工先 `git remote -v`，缺了就重加；`commit` 报 "empty ident" / `push` 无 remote 不是仓库坏了。stable-ts 内部直接调用名为 `ffmpeg` 的可执行文件：没有系统 ffmpeg 时把 imageio-ffmpeg 二进制软链成 `~/.local/bin/ffmpeg` 并加进 PATH（`audio_pipeline.py` 已内置）。ASR 对齐与渲染串行跑（2 GB 内存）。
- **audio_pipeline.py 可选字段**（写在 script.json）：`pause_after`（思考拍插在第几段之后，默认 1；018 的“给你三秒”在第 2 段末 → 2）、`pause_seconds`（默认 3）、`pause_cap_s`（默认 0.2）、`chars`（缺省自动数）。段 id 用 `01…07` 字符串，对应 `audio/NN.wav`。
- **场景边界别卡在段边界**：段末最后一个短语常是本段的“揭晓词”（018 §04 末“一样多”、§05 末“分毫不差”），下一段首句往往是过渡（“不信就算”“更狠的是”）。渲染器的场景切换应延到下一段的**第一个实义锚点**，否则揭晓文字只停 <1 s。
- **标签车道**：杯/物顶上的数值标签固定在 `y0−40` 一条车道；勺子/图标飞行路径峰值保持在 `y0−110` 以上或车道以下，飞行结束停靠点也不得压标签；举起某个杯子时隐藏它的标签并把它画在最上层（`wine_on_top`）。
- **揭晓段的“分层表示”**：交换/混合类题在揭晓时改画“排序后的分层”（水杯淡色 91 + 琥珀条 9 / 酒杯底部淡色条 9），两条同厚即“同一缺口的两面”；数值仍来自状态模型，只是显示顺序不同——分镜里要写明“分层为示意，不是物理分布”。
- **响度**：用 ffmpeg `loudnorm` 两遍（I=-15, LRA=11）；TP 目标设 −1.5 给 AAC 编码留过冲余量，成片再用 `ebur128=peak=true` 实测（018：设 −1.5 → 成片 −1.4 dBTP；设 −1 时成片 −0.9 超标）。只用 pyloudnorm 增益 + 峰值缩放会被真峰卡在 −19 LUFS。
- **assets 大库提交**（700 MB+）：`git clone --filter=blob:none --depth 1 --no-checkout` + `git sparse-checkout set episodes/LOGIC-0NN` + `checkout main`，只下当集目录；manifest 用 `git -c core.quotepath=off ls-files -z -s` 取 blob id，字节数取工作区文件或上一版 trees API（同 blob 同大小），推送后用 trees API 逐条核对（键 ⊆ 远端 blob、sha 与 size 相等，manifest 不含自身）。`.gitignore` 会挡 `**/audio-qa.json`，QA 记录进进度库。
- **证据目录命名**：文案版本与成片版本编号会错位（文案 r2 → 成片 r1）。进度库证据用 `logic-0NN/r1|r2`（文案）与 `logic-0NN/production-r1`（成片）分目录，附 README，别把成片证据覆盖进文案目录。
- **全帧扫描再渲染**：`--preview` 只采样事件点 +0.25/+0.9 s，弹入动画的极小尺寸帧（pop 起始 k≈0.05）不会被采到；018 r2 正式渲染在 60 s 处因 `ellipse x1<x0` 崩溃、mix 把半截视频封装了出去。渲染前先跑一遍 0.1 s 步长的 `frame(t)` 异常扫描（~1 分钟），所有按 `pop()` 缩放的自绘图形（奖章/本子/气泡/叉）都要有“太小就不画”的守卫。
- **依赖不持久**：pip 包、whisper 模型缓存、`.cache` 下的稀疏克隆在回合之间都会消失；每回合开工先装依赖（后台 start_process），素材/音频/成片放工作区。
- **封面道具**：先把 `draw_spoon` 之类的道具函数写成“先画内容再旋转”，否则倾斜的勺子会丢内容；封面复用同一函数合成（杯+勺）。

## 步骤 10：沉淀（细则）

每轮结束前问自己三件事并各写一条：
1. 这轮**用户指出**了什么我没发现的？→ 规则进 production-standard §2.3 对应小节。
2. 这轮**我自己返工**了什么？→ 同上。
3. 这轮**流程**哪里绕了路？→ 更新本文件。

## 与 `tools/pipeline_check.py`

`python tools/pipeline_check.py <episode_dir>` 检查项目目录是否具备每一步的产物与门字段（script.json.logic_check.sentence_checks、storyboard.md、checks/enc-first6s.jpg…），缺项直接列出。它只检查"有没有"，不替代人工看图。

## 候选复用时的逻辑复核

- 旧候选的脚本通过不等于逐句文案通过；恢复提案时检查近似百分比、分母权重、参照系和概率前提是否与模型一致。人数/顺序类概率题明示随机机制、可观察信息、无并列及是否可回头。
- 声称最优须覆盖允许的策略空间或给出证明；只比较几种阈值不能冒充全策略证明。区分有限规模的精确最优与大样本近似。
- 把公式重复计算一遍不是独立物理模拟；说明验证方法的真实范围。无来源的历史轶事删除或另查可信来源，不随数学答案一起标成已验证。
- 恢复待选题继续同一候选轮次并披露历史来源，未选不占号；新检查点须同步更新标题及交接入口，避免完成项仍显示启动中。

- 文案检查器的容差和关键词命中不替代语义门：首问自动扫描可能取到反问或开场赌注问句，应定位第一个完整题设问句，按目标语速加停顿复算，仍须满足用户首问上限。五拍关键词缺失先人工映射段落，保留工具原输出与复核理由，不为凑正则生硬改稿。思考拍的旁白位置、段末插入参数和分镜必须一致。

- 用户要求“更有趣/动画更多”只授权修订，不等于当前稿或后续媒体已放行。保留已批准样式与逻辑骨架，给出可数的新增动画事件、幽默位置和时长差值；新增动作不能改变题设状态或抢先揭晓。笑点集中在赌注与转场，证明句和最终结论不塞梗。修订后重新跑逻辑与预算门，再交用户确认。

- 用户明确要求“首句有梗且直奔主题”时，首句应把核心道具/错误判断/赌注后果与笑点合在一起；仅报题目和赌注不等于已有笑点。先给少量开头方向供选，首帧同步出现题设物件，1秒内动作，5秒内冲突清楚；不能靠延后的笑话补首句。缩开头不删参照系、随机性等必要前提；换新首句后删重复梗、重算首问时间。可量测开头条件不能表述为留存保证，真实效果须由用户提供的发布数据验证。

- 多个开头被用户否定后，不只对同一牵强赌注换同义词；重新检查笑点是否源于题目的反直觉。可提出“答案前置、追问原因”和“保留猜答案”两种结构，但前置答案会改变悬念、思考拍及揭晓段，必须明确取舍并获用户选择；不能开头泄答案后仍伪装中段首次揭晓。被否定的具体候选保存在私有进度，不写成通用禁词。
